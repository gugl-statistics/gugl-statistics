1The toy ECC scheme

Encrypting and decrypting a message with the toy scheme from Part 1.

Recap of the scheme (Part 1)

The scheme from Part 1 is an ElGamal/ECIES-style hybrid scheme on the secp256k1 curve (the Bitcoin curve), i.e. the curve y² = x³ + 7 over the prime field Fp with p = 2²⁵⁶ − 2³² − 977. It has a standard base point G whose order n is a prime of about 2²⁵⁶. "Hybrid" means that the elliptic curve is only used to agree on a secret, and the actual message is encrypted with symmetric tools (SHA-256 and HMAC).

The only thing that makes it a toy is the private key: instead of being chosen in [1, n−1] it is chosen in [1, 2²⁰], so there are only 1,048,576 possible keys. Everything else is the standard construction.

The keys and their roles

KeyWho has itRole
d (private key)only the recipientan integer in [1, 2²⁰]. It is the only thing needed to decrypt. Never sent anywhere.
Q = d·G (public key)everyonea point on the curve. Anybody can use it to encrypt to the recipient. Getting d back from Q is the elliptic-curve discrete log problem (ECDLP).
k (ephemeral key)only the sender, for one messagea fresh random 256-bit scalar for every message, thrown away afterwards. It makes encryption randomized.
R = k·Gsent with the ciphertextthe sender's "half" of the key exchange. Lets the recipient rebuild the shared point.
S = k·Q = d·Rsender and recipientthe shared secret point (Diffie-Hellman). Both get the same point because k·(d·G) = d·(k·G).
kenc, kmacsender and recipientsymmetric session keys derived from the x-coordinate of S with SHA-256. One encrypts, one authenticates.

Main steps of the algorithm

Key generation

  1. Pick d uniformly in [1, 2²⁰].
  2. Compute Q = d·G (double-and-add) and publish it.

Encryption (sender, knows Q)

  1. Pick a random k ∈ [1, n−1].
  2. Compute R = k·G and S = k·Q.
  3. kenc = SHA256(xS‖01), kmac = SHA256(xS‖02).
  4. c = m ⊕ keystream(kenc) where the keystream is SHA256(kenc‖0), SHA256(kenc‖1), …
  5. tag = HMAC-SHA256(kmac, c).
  6. Send (R, c, tag).

Decryption (recipient, knows d)

  1. Check that R is really a point on the curve (and not the point at infinity).
  2. Compute S = d·R.
  3. Derive the same kenc, kmac.
  4. Recompute the HMAC of c; if it is different from tag, reject.
  5. m = c ⊕ keystream(kenc).
Why it works: the sender uses k·Q = k·d·G, the recipient uses d·R = d·k·G. Same point → same keys → XOR cancels out. An eavesdropper sees Q and R but not k or d, so it can't compute S.

2The Caesar cipher

Encrypting and decrypting the same message with a shift.

The Caesar cipher maps every letter to the letter k positions later in the alphabet. If we number the letters A=0, …, Z=25:

Ek(x) = (x + k) mod 26     Dk(y) = (y − k) mod 26

The key is just the shift k ∈ {0, …, 25} and the same key is used to encrypt and decrypt (symmetric). In my implementation upper/lower case is kept and anything that is not a letter (spaces, punctuation, digits) is left as it is.

3Comparing the two schemes

Encryption/decryption procedures, key spaces and statistical properties.

Similarities

  • Both are built on a group operation. Caesar is addition in Z26 and decryption is adding the inverse (−k). The ECC scheme works in the group of points of the curve, where the "addition" is point addition, and the key pair is linked by repeated addition (Q = G + G + … + G, d times). I found this a nice parallel: in both cases the secret is "how many times you add something".
  • Both are correct only if you have the right key: decryption is the exact inverse of encryption, with the wrong key you get garbage (Caesar) or a rejection (ECIES, because of the MAC).
  • Both follow Kerckhoffs' principle: the algorithm is public and all security is in the key.
  • In this homework both have a key space small enough to search. 26 keys for Caesar and 2²⁰ for the toy ECC scheme. This is the common weakness that sections 4 and 5 exploit, in very different ways.

4Statistical cryptanalysis of the Caesar cipher

Recovering the shift from the ciphertext only, using the letter distribution of English.

Reference distribution (the "corpus")

As the known-language corpus I used 8 public-domain books from Project Gutenberg (three Austen novels, three Chesterton novels, Moby Dick and Edgeworth's The Parent's Assistant), for a total of 4,134,649 letters. From them I computed the probability pi of each letter, and also the probability of each pair of letters (bigrams) for the optional part. To test the attack fairly I used a different book, Alice in Wonderland, that is never used to build the statistics.

The algorithm (chi-squared + exhaustive search over the shifts)

  1. Keep only the letters of the ciphertext and convert them to upper case. Let N be their number.
  2. For every candidate key k = 0 … 25: decrypt with k and count how many times each letter appears (Oi).
  3. Compare with what English would give, Ei = N·pi, using χ²(k) = Σi (Oi − Ei)² / Ei.
  4. Return the key with the smallest χ²: its decryption "looks the most like English".

This works because Caesar does not change the shape of the distribution, it only rotates it, so exactly one of the 26 rotations lines up with English. Since there are only 26 keys we can afford to try all of them, so it is really "frequency analysis + exhaustive search" together.

Effectiveness and limitations

Effectiveness. The χ² attack is very reliable once the text is not tiny: about 49% correct at 5 letters, 76% at 10, 94% at 20, ≥98% from 30 letters and 100% from 75 letters on. So a normal sentence is already enough. With a few hundred letters it basically never fails, and it is instantaneous (26 × N operations).

Limitations (the last three buttons in the demo are examples I found where χ² fails for every key from 1 to 25):

  • Short texts. With 5-10 letters the counts are too noisy and many shifts give a similar χ². For "Fix my van" (8 letters) the χ² attack gets the key wrong for all 25 shifts, and so does the bigram method. Sometimes the correct key is still near the top of the ranking, so a human can look at the first few candidates.
  • Texts that are not "average English". The method assumes the plaintext follows the corpus distribution. "Jazz fans buzz with joy at a big gig in a dim club" has no E at all and lots of Z, J, B, G, so even with 38 letters χ² picks a wrong shift every time (the bigram method gets it right, see below).
  • Wrong language. It needs to know the language. Italian has many more A and I and almost no K, W, Y, so English statistics fail on "La zia Lucia va in Sicilia a luglio". Interestingly the English bigram model still finds the key here, because common pairs like "LA", "IN", "IA" also exist in English. With longer Italian texts χ² often works too, but the right fix is to use an Italian corpus.
  • It ignores order. χ² looks only at single-letter counts, so it throws away all the information in letter order. This is why the n-gram methods below are better on short texts.
  • Non-text plaintexts. If the plaintext were random letters, no statistical method could pick one of the 26 decryptions. Caesar would still be broken by trying all keys, but you wouldn't know which output is the right one without some other information.
  • It only works because Caesar is a single fixed substitution. Already with Vigenère you would first need to find the key length.

5Attacking the toy ECC scheme

Recovering the private key by exploiting the restricted key space.

The ciphertext of the ECC scheme looks random (section 3), so a statistical attack like the one on Caesar gets nowhere. But we don't need the ciphertext at all: the public key Q = d·G is public, and we know that d ≤ 2²⁰. So we can just solve the discrete log in this small range, and with d we can decrypt every message ever sent to that key.

Attack 1: brute force

Start from T = G and keep adding G: G, 2G, 3G, … until T = Q. Each step costs one point addition, so in the worst case 2²⁰ ≈ 10⁶ additions (on average half of that). In my Python code it took 11.3 s for d = 701,495.

Attack 2: baby-step giant-step (BSGS)

This is a time-memory trade-off. Let m = ⌈√2²⁰⌉ ≈ 1025. Every d in the range can be written as d = i·m + j with 0 ≤ i, j ≤ m. Then:

Q = (i·m + j)·G  ⇔  Q − i·(m·G) = j·G

  1. Baby steps: compute j·G for j = 0 … m−1 and store them in a hash table (point → j).
  2. Giant steps: compute Y = Q, Q − mG, Q − 2mG, … and look each one up in the table.
  3. When Y = Q − i·mG is in the table with value j, return d = i·m + j.

This needs at most about 2m ≈ 2,050 point operations instead of 10⁶, and memory for ~1,025 points. In Python it took 0.03 s. After finding d it's easy to check it (compute d·G) and then decrypt normally (and the HMAC confirms that the key is right).

Why this would not work against properly configured ECC

With a real key, d is uniform in [1, n−1] with n ≈ 2²⁵⁶. Brute force then needs ~2²⁵⁵ additions on average, and the best generic algorithms (BSGS, Pollard's rho) need about √n ≈ 2¹²⁸ operations. That's why a 256-bit curve is said to have "128-bit security". BSGS would also need a table of 2¹²⁸ points, which is more memory than exists. Pollard's rho needs almost no memory, but the time is the same. For secp256k1 no special structure is known that gives a much faster attack (the curve has prime order, so no small subgroups to exploit, and it is not one of the weak curve families where the discrete log can be moved to an easier group). The attack in this section only works because we chose to restrict d: the group is still huge, the key space isn't.

Optional: other attacks, and where the weaknesses come from

Weaknesses caused by the restricted key space

  • Brute force and BSGS (above).
  • Pollard's kangaroo (lambda) method: designed exactly for a discrete log known to lie in an interval of width w. It needs about 2√w operations like BSGS but only constant memory, so it would be the choice for larger intervals, e.g. 2⁶⁰.
  • Precomputation for everyone: since all users pick d in the same range, an attacker can compute the table of all 2²⁰ points d·G once (a few tens of MB) and then break any public key of any user with a single lookup. Small key spaces make attacks reusable.
  • The size of the toy key space is basically like a 20-bit password. Even Caesar's problem is the same idea in a smaller version.

Weaknesses that could come from the design of the toy scheme itself

These are not about the size of d, they would apply even with a full 256-bit key, so they have to be avoided in the design:

  • Ephemeral key k. If k were also taken from a small range (for example reusing the same "toy" generator), an attacker would solve R = k·G with BSGS, compute S = k·Q and decrypt one message without knowing d. If k is reused for two messages, the keystream is the same and c₁ ⊕ c₂ = m₁ ⊕ m₂, which can be attacked with… statistics of the language, just like Caesar. My implementation uses a fresh 256-bit random k each time to avoid this.
  • No authentication. Without the HMAC, the XOR-keystream encryption is malleable: flipping a bit of c flips the same bit of the plaintext, and nobody notices. The "flip one bit" button in section 1 shows that the tag catches this.
  • No point validation. If the decryption didn't check that R is on the curve, an attacker could send points on a different (weaker) curve and learn d piece by piece (invalid-curve attack). My code checks it before using R.
  • Bad randomness. If d or k come from a weak random generator (e.g. Math.random() instead of crypto.getRandomValues), they might be predictable.
  • Implementation side channels. My double-and-add is not constant time (it does an extra addition for each 1 bit of the scalar), so in theory timing could leak bits of d. This is an implementation issue rather than a scheme issue, but it's worth mentioning. Also the ciphertext length reveals the message length.

6Conclusions

The two schemes look very different (one rotates letters, the other uses 256-bit elliptic-curve arithmetic) but in this homework they share the same fatal weakness: a key space small enough to try. What changes is how the attacker gets around it. Caesar leaks the statistics of the language, so the key can be recovered just by counting letters, and with χ² this works for basically any sentence longer than ~30 letters. The ECC scheme leaks nothing statistically, its ciphertext is indistinguishable from random bytes, but the public key plus the small range of d is enough to solve the discrete log with BSGS in a fraction of a second.

The lesson for me is that a strong algorithm doesn't save a weak key: the security of secp256k1 comes from the 2²⁵⁶ size of the key space, and once that is reduced to 2²⁰ the curve is only as strong as a 20-bit password. With a properly chosen key the same attacks would need ~2¹²⁸ operations, which is impossible.

Show the core of the BSGS attack 
def bsgs(Q, limit=2**20):
    m = isqrt(limit) + 1
    table, T = {}, INF              # baby steps: j*G
    for j in range(m):
        table[T] = j; T = add(T, G)
    step = neg(mul(m, G))           # -m*G
    Y = Q
    for i in range(m + 1):          # giant steps: Q - i*m*G
        if Y in table:
            return i*m + table[Y]
        Y = add(Y, step)
    return None

def chi2(L):                        # L = letters only, upper case
    n = len(L); cnt = Counter(L)
    return sum((cnt[c] - n*p)**2 / (n*p) for c, p in zip(ALPHABET, EN_FREQ))
